# Bug hunt, 2026-09-28

A read-only hunt through the JS8 app for likely bugs: **no code was
changed**. Each entry says where, what goes wrong, how sure we are, and a
possible fix. Confidence: **confirmed** (read in the code, the failure path
is clear), **likely** (the code allows it; not reproduced), **possible**
(worth a look).

Found by Claude Code, reading the code on `main` at `6e21302`.

## Findings

### 1. Only one automatic reply can wait; a second one overwrites it — confirmed

`src/dialog_js8.c`, `auto_send()` (`pending_auto = *r; /* newest wins */`).
While we're transmitting, a list is open or the keyboard is up, an
automatic reply waits in a single slot. If a second one arrives before the
first goes out, the first is lost. Example: N0XYZ's `MSG` arrives (our ACK
waits), then W1ABC's heartbeat arrives (its HB ACK replaces our ACK): N0XYZ
never gets the ACK, and desktop N0XYZ thinks the message failed. Same for a
held-message delivery or a relay waiting behind another reply. Desktop
queues every reply (`m_txMessageQueue`, by priority).
**Fix:** a small queue (say 8) of pending replies, oldest first, deduplicated
by text; drop stale ones after `PENDING_AUTO_MS`.

### 2. Only one held-message delivery is tracked at a time — confirmed

`src/dialog_js8.c`, `deliver_start()` / `deliver_end()` (`deliver_tx`, one
slot). A delivery counts once its transmission ends in full. If a second
delivery is queued before the first has ended (two stations fetch their
messages, or `QUERY MSG 3` then `QUERY MSG 4` back to back), the second
`deliver_start()` overwrites the first, so the first message is never
marked delivered. It is then offered again on every `QUERY MSGS` and HB
ack, and pushed with `RETRIEVE MSG`.
**Fix:** keep a short list of in-flight deliveries keyed by sent text.

### 3. Inbox Reply takes any word after "FROM" for the original sender — confirmed

`src/js8/inbox.cpp`, `delivered_signature()`, used by the Inbox view's
*Reply to X via ...* / *Reply to X* items. The regex
`(?:^| )FROM (\S+)(?: NEXT MSG ID ...)?$` matches ordinary text: a message
"I'M AWAY FROM HOME" offers **"Reply to HOME"**, and a reply would go to a
callsign "HOME". Desktop's `MessagePanel::configureReplyButton()` also
requires `Varicode::isValidCallsign(originalSender)`. We only reject `@`.
**Fix:** require a valid callsign (js8core's `is_valid_callsign()`).

### 4. A message to "VE7NHW/P" counts as to us when we're VE7NHW — likely

`src/js8/classify.cpp` (`to_me` compares base callsigns) and the auto-reply
code that trusts it. Desktop's `toMe` is exact: our call or our base call.
So with AUTO on we answer queries, ACK messages and pass relays addressed to
a different station that shares our base call (a portable operator, a
club's /P, a second radio). Desktop would stay quiet.
**Fix:** match desktop: the target equals our call or our base call.

### 5. Only one offered reply at a time — confirmed (by design, but it bites)

`src/dialog_js8.c`, `offer` (one slot). With AUTO off, each query or
message to us offers its answer on **Reply**. A second station's question
replaces the first's offer, so selecting the first station and pressing
Reply gives a blank message instead of their answer. Desktop has the same
single outgoing box, so this matches desktop, but the Stations/selection
model makes it easier to hit here.
**Fix (if wanted):** one offer per station.

### 6. A station's grid is taken from any grid-shaped word in any message — confirmed

`src/js8/classify.cpp`, `find_grid()`, used by `StationList::add()` for
every message a station sends. After looking for `GRID xxxx`, it falls back
to the **last word shaped like a grid anywhere in the text**. So "N0XYZ:
K2XYZ MY DAUGHTER LIVES IN EM12" sets N0XYZ's grid to EM12, as does naming
someone else's grid ("W1ABC IS FN42"). The wrong grid then shows in the
Stations view, drives the distance and bearing, **and goes into the log**
(the Log popup fills Grid from the station). The QSO tracker
(`src/js8/qsolog.cpp`, `QsoTracker::received()`) does the same with every
message to us, and the Log popup prefers *its* grid. Desktop only takes a
grid from heartbeats, CQs and GRID commands.
**Fix:** take grids only from heartbeats, CQs, `GRID` replies and
`@APRSIS GRID`, as desktop does, in both places.

### 7. Any message to us switches heartbeats off, even a garbled one — confirmed

`src/dialog_js8.c`, `handle_incoming()` → `js8_starts_qso()` →
`qso_started()` → `hb_pause()`, which turns **HB and HB ACK off until you
switch them back on** (the comment says this was a deliberate choice).
But `starts_qso()` (`src/js8/autoreply.cpp`) is true for **any** message
to our call except a heartbeat ack: someone's `SNR?`, `QUERY MSGS`, a
relay passing through us, a `MSG TO:` left for someone else. It doesn't
check `low_confidence` either, so a garbled decode that happens to contain
our call does it too (everything else ignores low-confidence decodes). So a
radio left running as a heartbeat/relay station goes quiet after the first
automated query, and stays quiet. The same call also stops auto CQ.
Desktop only *pauses* heartbeats while a QSO is going on and resumes them
by itself.
**Fix:** skip low-confidence decodes; pause only for a real QSO (plain
text, or a reply to someone we called); ideally pause rather than switch
off.

### 8. Once the inbox is full, new messages aren't saved and aren't announced — confirmed

`src/js8/js8_ops.cpp`, `keep()`: whether a message is new is worked out as
`resend = inbox->box.size() == before`. `Inbox::add()` (`src/js8/inbox.cpp`)
drops the oldest message when the inbox holds more than 200, so from then
on **every new message leaves the size unchanged and counts as a resend**:
- the inbox file isn't saved (`if (!st.resend && ...) save()`), so a power
  cut before the next inbox change loses it;
- `stored_received()` shows no "New message from ...", adds no info row
  and doesn't beep;
- the sender still gets our ACK, so they think it arrived.

The same happens to held messages (`MSG TO:`) once 100 are held.
**Fix:** have `add()` say whether it added a message (for example, compare
the returned id with the next id), rather than comparing sizes.

### 9. The Inbox list shows only the 50 newest messages — confirmed

`src/dialog_js8.c`, `inbox_show(0)`: `INBOX_ROWS 50`, but the inbox keeps
200 messages (and 100 held ones). The title says "Inbox: 120 messages, 3
new", but only the 50 newest can be opened. An unread message older than
those can't be read, deleted or marked read, so "MSG 1 NEW" and the green
Inbox button never go away.
**Fix:** a longer list (or paging), or keep 50 in the inbox.

### 10. The band keys change band in the middle of a transmission — confirmed

`src/dialog_js8.c`, `band_cb()` → `load_band()` → `retuned()`: no
`js8_tx_busy()` check. The Freq popup's `use_presets()` and
`parse_custom()` both refuse with "Not while sending - Stop TX first", but
the band keys don't. Pressing one while a multi-frame message is going out
sends the rest of it on the new band. Worse if a frame is on the air:
`tx_player_play()` (`src/tx_player.c`) reads the dial when the frame
starts, and when it ends it sets the radio back to **that** dial with
`radio_set_freq()`. So the radio can be left tuned to the old band while
the screen and settings show the new one, and it stays that way until the
next retune.
**Fix:** the same "Not while sending" check in `band_cb()`.

### 11. A reply that was waiting goes out on the new band — likely

`src/dialog_js8.c`, `retuned()` clears the station selection and the
decoder, but not `pending_auto`, `offer` or `deliver_pending`. The Freq
popup is itself a popup, and any automatic reply that arrives while a
popup is open waits in `pending_auto` for up to 2 minutes. So: open Freq,
an ACK or query answer arrives for a station on 40 m, pick 20 m, the popup
closes and `hb_tick()` sends the 40 m station's reply on 20 m.
**Fix:** drop `pending_auto` (and the offer) in `retuned()`.

### 12. The Log prompt can open by itself and then stop all automatic TX — likely

`src/dialog_js8.c`, `log_offer()` opens the Log popup when a two-way QSO
ends with 73 or SK. Automatic transmissions count towards "two-way"
(`ui_tx_status()` passes every message we send to `js8_qsos_sent()`), so
an unattended station can "have a QSO": they ask `SNR?`, AUTO answers, they
send "TNX 73". While **any** popup is open, `auto_send()`, `hb_tick()`,
`push_tick()` and `auto_cq_tick()` all wait, and a waiting reply is thrown
away after 2 minutes (`PENDING_AUTO_MS`). So one automatic exchange can
leave a relay/heartbeat station silent until someone closes the popup.
**Fix:** don't count automatic transmissions as our side of a QSO, and/or
don't let the Log popup hold up automatic replies.

### 13. "73" anywhere in a message ends the QSO — likely (small)

`src/js8/qsolog.cpp`, `ends_qso()`: any word "73", "SK" or "RR73" ends
the QSO and offers to log it: "I'M 73 NEXT WEEK" or "73 DEGREES HERE" does
too, in the middle of a QSO. A QSO is offered only once (`offered`), so
if you close that early prompt, the real end isn't offered.
**Fix:** look only at the last word or two of the message.

### 14. Stations view: with a locked station, the cursor jumps back every 5 s — likely

`src/dialog_js8.c`, `tx_timer_cb()` rebuilds the Stations view every 5 s
(to update the ages), and `rebuild_station_rows()` puts the cursor back on
the **selected** station. With a station locked, turning the knob only
scrolls, but 5 s later the cursor snaps back to the locked station, so you
can't read further down the list.
**Fix:** while locked, keep the cursor on the station it was on (or on the
same row), not on the selection.

### 15. Hold Speed takes the cursor's station, not the selected one — likely (small)

`src/dialog_js8.c`, `selected_speed()` reads the row under the cursor.
Before the lock (beta 4) the cursor and the selection were always the same
station; now they aren't. With a station locked and the cursor elsewhere,
holding Speed switches to the **cursor** station's speed, and
`speed_warn()` names the locked station but compares the cursor row's
speed.
**Fix:** use the selected station's speed (from the Stations list).

### 16. Inbox and held-message saves can lose everything in a power cut — possible

`src/js8/inbox.cpp`, `Inbox::save()` / `HeldMessages::save()` write a
`.tmp` file, `fsync` it and `rename()` it over the old one. On the DATA
partition (FAT32), `rename()` over an existing file isn't atomic, and the
directory is never synced. A power cut at the wrong moment can leave only
`js8_inbox.txt.tmp`; `load()` never looks at `.tmp`, so the inbox then
starts empty, and the next save overwrites `.tmp` too. These saves also
run on the GUI thread, and `fsync` on an SD card can take a noticeable
time.
**Fix:** on load, fall back to the `.tmp` file when the real one is missing.

### 17. Station view asks the log database about every station every 5 s — possible (speed)

`src/dialog_js8.c`, `rebuild_station_rows()` calls
`qso_log_search_worked()` (a database lookup) for every listed station,
up to 200, on every rebuild: every 5 s and after every message while the
Stations view is showing. On a busy band this may make the GUI stutter.
**Fix:** cache worked-before per call, and refresh it after a log save.

### 18. Info rows disappear whenever the list is rebuilt — confirmed (small)

`src/dialog_js8.c`, `rebuild_rows()` builds the list only from the
message history; info rows (`add_info_row()`: "Auto: N0XYZ SNR -05",
"Message from N0XYZ in the Inbox: ...", "QSO with N0XYZ ended: Log QSO",
"Held message 3 delivered", "Relaying ...") aren't in it, so they vanish
on every rebuild. Rebuilds happen when the Show filter changes, when you
leave the Stations view, every time the list reaches 200 rows, and, with
*Messages kept* set, as often as every 30 s (`msg_age_tick()`). Once the
list is full (200 rows) `add_info_row()` also drops new info rows
silently. So a notice can be gone before you look.
**Fix:** keep info rows in the history (a flag on the entry) so they
survive rebuilds.

### Smaller things

- **APRS length check counts the message ID** (`aprs_prepare()`): APRS
  allows 67 characters *plus* the `{NN}` ID, but the check counts the ID,
  so SMS/email/Winlink messages are cut to 63. Likely.
- **Long relay paths are cut short** (`JS8_PATH_LEN 48` in `js8_ops.h`):
  the inbox file keeps the whole path, but the C structs truncate it, so
  *Reply* on a message that came through several stations with long calls
  would send to a chopped callsign. Possible (needs a long path).
- **A typed log grid isn't checked or upper-cased** (`log_edit_done()`):
  "cn89" or "HOME" goes into the ADIF log as typed. Possible (small).
- **A RETRIEVE MSG notice that fails to queue isn't retried for 8 hours**
  (`push_tick()`): `js8_held_push_due()` marks the message told before
  `tx_queue_at()` runs. Unlikely to matter (queueing rarely fails there).
- **Garbage error text if the transmitter failed to start**
  (`tx_queue_at()`): `err` isn't initialised, and `js8_tx_send()` returns
  false without writing it when `tx` is NULL, so "JS8: %s" prints whatever
  was on the stack. Only after "JS8: cannot start transmitter".
- **The transmitter says "not busy" before the UI hears it finished**
  (`Transmitter::run()` in `src/js8/tx.cpp` clears `busy_`, then posts
  `on_done`). In that gap `hb_tick()` or `auto_send()` can queue the next
  message, and a new `deliver_start()` then replaces the delivery that
  `ui_tx_done()` is about to mark (makes finding 2 more likely).

## Checked and fine

The relay/command parser (`directed.cpp`), the transmitter's slot timing
(`tx.cpp`), APRS/POTA/SOTA formatting (apart from the ID count above),
frequency parsing, the Time Sync maths, the beep/TX interlock, the
assembler (it matches desktop, including merging stations within the
frequency tolerance), and the buffer sizes in the status and TX bars.
